机器人仿真、数据格式与通信及 Sim2Real 基础

发表于2026-11-15|更新于2026-11-22|机器人仿真
|浏览量:

引言

机器人从算法验证走向真实部署，需要同时处理模型、物理环境、软件通信、数据接口和执行安全等问题。仿真环境用于在可控条件下验证机器人模型与任务策略；机器人描述格式和通信框架负责组织本体结构及软件模块；Sim2Real
则进一步处理仿真系统与真实系统之间的差异。

这三个主题构成一条连续的工程链路：

  1. 仿真与评测：在虚拟环境中建立机器人和任务场景，验证运动、接触、控制与任务逻辑。
  2. 模型描述与系统通信：使用统一的数据格式描述机器人，通过通信接口连接感知、规划、控制和执行模块。
  3. Sim2Real：通过标定、系统辨识、域随机化、真实数据适配和分级验证，逐步提高策略在真实机器人上的可用性。

第一章 仿真环境概述与平台选择

1.1 机器人为什么需要仿真

机器人直接在真实环境中开发，通常需要占用设备、场地和操作人员。错误动作可能造成设备损伤、物体损坏，甚至引发人员安全风险。对于需要大量试错的学习型策略，完全依赖真机进行训练和验证，成本通常较高。

仿真环境能够提供相对可控的实验条件，主要价值体现在以下方面。

价值 具体作用
降低风险 在虚拟环境中测试错误动作，避免直接损伤真实设备
降低成本 减少对真机、场地和人工操作的持续占用
加快训练 可以加速仿真时间，并在条件允许时并行运行多个环境
批量生成数据 在不同场景和参数条件下采集观测与动作数据
便于复现 保存初始条件、参数和运行日志，重复执行同一实验以定位问题

仿真并不是为了完全取代真机，而是将大量早期验证和试错放在风险较低、成本较低的环境中完成。较合理的开发路径是：先进行仿真训练与筛选，再缩小仿真与现实之间的差距，最后开展小规模真机验证。

1.2 仿真任务场的组成

一个可用于机器人任务验证的仿真环境，不只是一个能够显示机器人模型的三维场景。它至少需要包含模型、运行闭环和验证机制。

1.2.1 模型

模型部分包括世界模型和机器人模型。

世界模型描述机器人所处的环境，例如地面、桌面、障碍物和目标物体。世界模型决定了任务发生的空间范围，以及机器人可能与哪些物体发生交互。

机器人模型描述机器人本体，包括连杆、关节、碰撞体以及质量和惯量等物理属性。机器人模型不仅要能够正确显示外观，还要能够为运动学、碰撞检测和动力学计算提供必要信息。

其中，视觉几何和碰撞几何承担不同职责：

  • 视觉几何（Visual）主要用于显示机器人和环境物体的外观。
  • 碰撞几何（Collision）用于计算机器人与环境之间是否发生碰撞，以及接触区域。
  • 惯性属性（Inertial）描述质量、质心和惯量，影响物体在力和力矩作用下的运动响应。

如果模型只有外观而缺少合理的碰撞体，仿真器就无法正确判断接触关系；如果质量和惯量设置不合理，物理响应也可能与真实系统明显不同。

1.2.2 运行闭环

仿真任务通常通过物理系统、传感器和控制器形成闭环：

  1. 控制器根据当前观测计算控制命令。
  2. 物理引擎根据控制命令和物理属性更新系统状态。
  3. 传感器根据更新后的状态生成图像、深度或关节状态等观测。
  4. 控制器读取新的观测，继续计算下一步命令。

这一过程持续运行，构成机器人与环境之间的交互闭环。

仿真步长、控制周期和传感器采样周期可能并不相同。工程实现中需要明确各自的时间尺度，并处理不同频率数据之间的同步关系。

1.2.3 验证机制

仿真任务还需要明确的成功判据和运行记录。仅观察机器人是否完成某个动作，通常不足以判断任务是否真正成功。

验证机制通常包括：

  • 成功判据：例如目标物体是否到达指定区域、抓取后是否保持稳定。
  • 运行日志：记录任务输入、状态变化、动作命令和异常信息。
  • 参数记录：保存模型参数、环境配置和随机种子。
  • 回放与回归测试：使用相同条件重新执行任务，判断修改前后的结果是否一致。

1.3 仿真中的常见错误类型

仿真环境能够让问题更早、更低成本地暴露出来。机器人任务中的常见错误可以归纳为四类。

错误类型 典型问题 可能表现
坐标错误 目标位置在不同坐标系之间转换错误 机械臂移动到错误位置
模型错误 关节限位、连杆尺寸或工具偏置设置错误 运动异常、目标不可达或发生碰撞
控制错误 命令没有发送成功，或目标本身不可达 机器人没有执行预期动作
任务错误 缺少接触判断、状态检查或失败重试 动作看似完成，但任务实际失败

这四类错误并不总是相互独立。例如，工具中心点（TCP）偏置错误可能先造成目标位姿偏差，随后引发碰撞或抓取失败。因此，排查时应沿着输入、几何模型、控制命令和任务判据逐层检查。

1.4 机器人仿真工具链的层级

机器人开发涉及不同层次的问题，仿真工具也因此形成不同分工。常见工具可以按验证对象划分为四个层级。

层级 主要内容 代表工具
数学与建模 FK、IK、Jacobian、碰撞几何 Robotics Toolbox、Swift
物理与场景 重力、碰撞、接触、传感器 Gazebo、MuJoCo、PyBullet、Isaac Sim
系统与中间件 模块通信、坐标、日志、硬件接口 ROS 2、TF、ros2_control
任务与基准 任务、观测、动作、数据和评价指标 LIBERO、RoboTwin

这些工具并不是同一类型的软件，也不需要在每个项目中全部使用。数学工具主要用于验证运动学和几何关系；物理仿真器用于验证接触、动力学和控制响应；系统仿真平台用于联调传感器、控制器与通信接口；Benchmark
则提供相对统一的任务和评价协议。

1.5 如何选择仿真平台

平台选择应由验证目标决定，而不是以软件数量作为开发完整度的衡量标准。

验证目标 重点关注 代表工具 典型通过条件
运动学与几何 可达性、FK/IK、碰撞几何 Robotics Toolbox、Swift 位姿正确，路径不存在几何碰撞
接触与动力学 质量、摩擦、碰撞和控制响应 MuJoCo、PyBullet 接触稳定，控制响应符合预期
系统联调 传感器、控制器和 ROS 2 接口 Gazebo、Webots 节点、TF 和硬件接口正常联通
高质量传感与数据 渲染、合成数据、并行环境 Isaac Sim 观测格式和数据分布满足任务
标准任务评测 任务、数据集、指标和实验复现 LIBERO、RoboTwin 在相同协议下能够重复比较

工程上通常优先确定一个主仿真平台，再根据专项问题选择其他工具进行补充验证。例如，已经在一个平台中完成场景、碰撞和传感器仿真，就没有必要为了形式完整而在多个引擎中重复搭建完全相同的场景。只有当交叉验证能够回答具体问题时，多平台验证才有实际价值。

1.6 本章总结

机器人仿真环境由机器人与世界模型、物理运行闭环以及验证机制共同组成。仿真能够降低开发风险和成本，加快训练与测试，并通过日志和回放提高实验可复现性。

选择工具时，应先明确需要验证的是运动学、动力学、系统通信、传感器数据还是任务性能，再选择相应平台。仿真成功并不自动意味着真机可用，仿真结果仍需要经过真实系统验证。

第二章 机器人模型描述与通信基础

2.1 机器人模型为什么需要标准化描述

仿真器和机器人软件系统需要读取机器人结构信息，才能计算关节运动、显示机器人模型、执行碰撞检测并连接控制接口。

如果每个软件模块都独立维护一套机器人结构参数，连杆尺寸、关节顺序、坐标系和限位很容易出现不一致。因此，需要使用统一的机器人描述格式组织本体结构和环境模型。

  • robot：机器人模型的根节点。
  • link：定义一个刚性连杆或刚性组件。
  • joint：定义两个 Link 之间的连接关系。
  • parent 和 child：指定关节连接的父连杆与子连杆。
  • axis：定义关节运动轴的方向。
  • limit：定义关节变量的上下限。

常见关节类型包括：

类型 含义 运动变量
revolute 转动关节 角度
continuous 连续转动关节 不设有限角度上下限
prismatic 移动关节 直线位移
fixed 固定关节 无运动变量

对于包含 NNN 个关节的简单串联开链机械臂，若计入基座，通常需要 N+1N+1N+1 个
Link。关节数量与自由度数量并不在所有机器人结构中完全等价；对于这里讨论的单自由度转动关节串联机构，NNN
个关节对应 NNN 个运动自由度。

完整机器人描述还可以包含以下信息：

  • origin：描述关节或几何体相对于参考坐标系的固定变换。
  • visual：描述显示几何。
  • collision：描述碰撞几何。
  • inertial：描述质量、质心和惯量。

因此，URDF
不只是机器人外观模型，也是运动学、碰撞检测和仿真配置的重要基础。

SDF（Simulation Description Format）同样采用 XML
结构，用于描述仿真模型及其环境。它不仅可以描述机器人模型，还可以组织完整的仿真世界。

  • model：机器人、桌面、杯子等场景模型。
  • sensor：相机、激光雷达等传感器。
  • plugin：扩展仿真功能的插件。

URDF 与 SDF 的侧重点不同：URDF 主要描述机器人本体的结构和关节关系；SDF
能够进一步组织仿真世界、物理属性、光照、传感器和插件。SDF
也可以单独描述模型，因此不能简单地把 SDF 理解为只负责环境、URDF
只负责机器人外观。

2.4 ROS 2：组织机器人软件模块

ROS（Robot Operating System）虽然名称中包含 Operating System，但它并不是
Windows 或 Linux
一类的传统操作系统，而是一套用于机器人软件开发的框架和通信中间件。

一个机器人系统通常由多个功能模块组成，例如：

  • 相机驱动：采集图像和深度信息。
  • 感知模块：识别物体并计算目标位姿。
  • 规划模块：生成运动轨迹。
  • 控制模块：将轨迹转换为控制命令。
  • 机器人驱动：执行命令并反馈状态。

ROS 通过
Node（节点）组织这些功能模块。节点可以运行在同一个进程中，也可以分布在不同进程或计算设备上。各模块通过明确的通信接口交换数据，减少功能之间的直接耦合。

2.5 Topic、Service 与 Action

ROS 2
提供不同的通信模式，选择时应考虑数据交互方式、任务持续时间以及是否需要进度反馈和取消机制。

接口 交互方式 适用对象 典型场景
Topic 异步发布与订阅 连续数据流 图像、点云、关节状态
Service 请求与响应 短时操作 查询参数、切换模式
Action 目标、反馈、结果和取消 长时间任务 导航、抓取、轨迹执行

2.5.1 Topic

Topic
采用发布—订阅模式。发布者将消息发送到指定话题，订阅者接收感兴趣的数据。发布者不需要等待所有订阅者处理完成，因此适合持续产生的数据流。

例如，相机以固定频率发布图像，感知节点订阅图像话题并进行处理。一个话题也可以被多个节点订阅。

Topic
本身不提供标准化的长任务进度和取消机制。虽然可以通过特定消息表达停止指令，但这与
Action 的任务生命周期管理不同。

2.5.2 Service

Service
采用客户端请求、服务端响应的模式。客户端发送请求，服务端处理后返回结果，适合查询参数、切换模式或重置仿真等短时操作。

Service
调用通常需要等待响应，不适合需要长时间执行、持续反馈进度并支持取消的任务。

2.5.3 Action

Action
面向持续时间较长的任务，包含目标（Goal）、过程反馈（Feedback）、最终结果（Result）以及取消请求（Cancel）。

例如，机械臂执行抓取任务时，客户端可以提交抓取目标，服务端在执行过程中持续反馈状态，任务结束后返回结果。客户端也可以请求取消任务，但服务端必须实现相应的中断处理逻辑。取消请求并不意味着机械臂会在任何情况下瞬间停止，底层控制和安全机制仍需正确处理。

2.6 TF：管理坐标系之间的变换关系

机器人通常包含多个坐标系，例如世界坐标系、机器人基座坐标系、相机坐标系和末端工具坐标系。不同模块输出的数据可能属于不同坐标系，因此需要统一管理坐标关系。

TF（在 ROS 2 中通常使用
tf2）用于维护坐标系之间随时间变化的变换关系，并允许其他模块按指定时间查询变换。

2.7 RViz 与 rosbag：运行观测和数据记录

RViz 是 ROS
生态中的三维可视化工具，可以显示机器人模型、坐标系、图像、点云和规划轨迹。它主要用于观察机器人系统的运行状态，本身不是物理仿真引擎。

rosbag 用于记录和回放 ROS
消息。一次抓取任务可以记录相机图像、TF、目标位姿、控制命令和关节状态。任务失败后，通过回放可以重新检查输入、状态变化和动作执行过程，从而提高问题的可复现性。

在实际排障中，可以沿着以下顺序检查：

  1. 输入是否存在：相机话题是否持续发布，消息内容和时间戳是否有效。
  2. 目标是否可执行：目标位姿是否带有正确的坐标系标识，TF
    是否存在，时间戳是否匹配，目标是否满足机器人运动约束。
  3. 命令是否被接受：Action
    是否接受目标，控制器是否处于可用状态，硬件接口是否正常。

如果机器人状态反馈没有正确发布，应优先检查机器人或仿真器的状态接口及对应
Topic。rosbag 可以记录这些消息，帮助复盘，但它本身不负责发布状态。

2.8 ros2_control：统一命令接口与状态接口

真实机械臂和仿真机械臂的底层执行方式不同。仿真后端通过物理引擎更新机器人状态，真实硬件则通过驱动和执行器产生实际运动，并通过编码器或其他传感器反馈状态。

如果上层控制逻辑直接依赖某一款仿真器或某种电机驱动协议，更换执行后端时就可能需要修改大量代码。

ros2_control 通过统一的命令接口（Command Interface）和状态接口（State
Interface），在上层控制器与底层硬件之间建立接口边界。

  • Command
    Interface    ：向执行端发送控制目标，例如关节位置、速度或力矩。
  • State
    Interface    ：从执行端读取机器人实际状态，例如关节位置、速度或力矩。

具体的硬件接口实现负责适配底层仿真器或真实设备的数据格式和控制协议。这样，上层控制逻辑可以在较大程度上保持一致。

需要注意，统一接口并不意味着仿真与真机可以无条件互换。关节限位、控制频率、动力学参数、驱动能力和安全机制仍然需要分别配置和验证。

2.9 本章总结

机器人描述格式、通信机制和硬件抽象共同构成机器人软件系统的基础：

概念 主要职责

机器人任务不是由单一模型独立完成的，而是由感知、坐标转换、规划、控制和执行等模块通过明确的数据接口协作完成。接口中的坐标系、单位、时间戳和动作语义必须保持一致。

第三章 Sim2Real 基础概念

3.1 从仿真成功到真机可用

Sim2Real（Simulation to
Reality）指将仿真环境中学习或验证得到的模型、策略和控制方法迁移到真实机器人系统中。

仿真中的成功并不意味着真机能够直接复现相同结果。真实系统与仿真模型之间可能存在几何、物理、控制、感知和环境等差异。

常见差异包括：

  • 标定差异：相机外参、工具中心点（TCP）和关节零位不准确。
  • 物理差异：摩擦、质量和柔性接触与仿真假设不一致。
  • 控制差异：控制频率、时延和执行器限速不同。
  • 环境差异：遮挡、线缆、人员活动和安全边界等真实条件未被仿真充分覆盖。

3.2 Sim2Real 差距的五个环节

3.2.1 感知差距

真实环境中的光照、噪声、遮挡和物体材质会改变传感器观测。仿真中训练的视觉模型可能依赖某些固定外观特征，在真实相机图像出现反光、阴影或遮挡时，识别和定位性能可能下降。

3.2.2 几何与装配差距

几何差距主要来自相机外参、TCP 和关节零位等参数不一致。

例如，相机安装位置发生偏移后，即使视觉模型准确识别了目标在相机坐标系中的位置，转换到机器人基座坐标系时仍可能产生系统性误差。

TCP
标定不准确也会导致末端法兰位置与实际工具中心点不一致，进而影响抓取位置和接触姿态。

3.2.3 动力学与接触差距

仿真中的质量、摩擦、碰撞几何和柔性接触模型可能与真实物体不同。

例如，仿真中的夹爪能够稳定抓住杯子，但真实接触面的摩擦系数较低，杯子在抬升过程中就可能滑落。此时，单纯修改
VLA 的输出不一定能够解决问题，还需要检查物理属性和控制执行条件。

3.2.4 控制与时序差距

真实机器人存在通信延迟、推理延迟、控制频率限制、执行器速度限制和输出饱和等问题。

模型输出动作的频率与底层控制器的运行频率通常不同，需要设计动作保持、插值或其他时间适配机制。若模型要求的动作超过执行器能力，真实机器人也无法完整执行。

3.2.5 任务与安全差距

真实环境中的场景可能发生变化，机器人周围还可能存在人员、线缆和其他设备。任务策略除了完成目标，还必须遵守设备工作范围和人员安全边界。

因此，Sim2Real 不能只关注任务成功率，还应考虑碰撞、异常停止和安全约束。

3.3 迁移方法一：标定与系统辨识

标定与系统辨识的目标，是通过真实系统的测量和测试结果修正模型参数，使仿真系统的几何关系和动态响应尽可能接近真实系统。

两者关注的对象有所不同。

方法 主要对象 典型参数
标定（Calibration） 几何关系与参考基准 相机外参、TCP、关节零位
系统辨识（System Identification） 物理和动态响应 质量、惯量、时延、带宽

3.3.1 标定

相机外参描述相机坐标系与机器人基座或其他参考坐标系之间的空间关系。外参偏差会影响视觉目标到机器人坐标系的转换结果。

TCP（Tool Center
Point）是工具中心点。安装夹爪或其他末端工具后，实际执行任务的位置通常不等于机械臂法兰中心，需要标定法兰与工具中心点之间的固定变换。

关节零位定义关节变量的参考位置。若真实编码器零位与模型定义不一致，相同的关节角度指令可能对应不同的实际姿态。

3.3.2 系统辨识

系统辨识通过向真实系统施加已知测试输入，并观察系统输出，估计影响运动响应的参数。

例如：

  • 质量和惯量会影响机器人及物体的动力学响应。
  • 时延会影响命令到达和状态反馈的时间关系。
  • 带宽反映系统对变化输入的响应能力。

3.3.3 真实系统与仿真模型的对比

一个可执行的流程是：向真实系统和仿真模型施加相同的测试命令，分别记录关节轨迹：

qreal(t),qsim(t)q_{\mathrm{real}}(t),\qquad q_{\mathrm{sim}}(t) qreal​(t),qsim​(t)

然后比较两者的位置、速度、接触行为和响应时延。根据差异估计并更新模型参数，再使用同一测试命令重复执行，检查轨迹间误差是否减小。

为了使比较有意义，测试时应尽量保证初始状态、输入命令和时间基准一致。若测试条件本身发生变化，就很难判断轨迹差异究竟来自参数更新还是实验条件变化。

3.4 迁移方法二：域随机化

域随机化（Domain
Randomization）不是把仿真模型调整成某一个固定的真实系统，而是在训练期间主动改变仿真环境中的参数，使同一个策略接触多种条件。

常见随机化对象包括：

随机化维度 示例
光照 强度、方向和颜色变化
纹理 桌面、物体表面材质变化
摩擦 机器人与物体、物体与地面之间的摩擦变化
质量 目标物体质量变化
初始位置 物体在工作空间中的位置和姿态变化
传感器噪声 图像噪声和测量误差变化

训练过程中，同一个策略需要在不同随机场景中完成任务。这样可以降低模型对单一光照、纹理、物体位置或物理参数的依赖，提高对环境变化的适应能力。

域随机化的范围应当具有物理合理性。随机化范围过窄，可能无法覆盖真实变化；范围过宽或生成不合理场景，则可能降低训练效率，甚至让策略学习到与实际任务无关的行为。

域随机化与系统辨识并不冲突：

  • 系统辨识根据测量结果修正仿真参数，使仿真更接近已知真实系统。
  • 域随机化围绕合理范围改变参数，使策略适应不同条件。

实际项目可以先完成关键参数标定，再围绕真实参数及其不确定范围进行随机化。

3.5 迁移方法三：少量真实数据适配

仿真无法完全覆盖真实系统中的所有差异，因此可以在仿真预训练之后，采集少量真实机器人数据，对策略进行适配更新。

典型流程如下：

  1. 大规模仿真数据：覆盖不同任务和场景变化。
  2. 仿真预训练策略：使用仿真数据得到初始策略 π0\pi_0π0​。
  3. 采集少量真实数据：记录真实环境中的成功、失败和执行轨迹。
  4. 适配更新：通过微调或残差校正修正策略。
  5. 部署策略：得到适配后的策略 π∗\pi^*π∗。

3.5.1 微调

微调（Fine-tuning）是在预训练模型的基础上，利用真实数据继续更新模型参数。它可以改变模型原有的观测—动作映射，使策略适应真实环境中的新数据分布。

微调不一定意味着重新训练全部参数，具体更新范围取决于模型结构、数据规模和训练方案。

3.5.2 残差校正

残差校正可以保留原有策略，并额外学习一个动作修正量。一种简单表达为：

afinal=abase+Δaa_{\mathrm{final}}=a_{\mathrm{base}}+\Delta a afinal​=abase​+Δa

其中，abasea_{\mathrm{base}}abase​ 是原始策略输出，Δa\Delta aΔa
是额外学习的修正量。实际使用时，必须保证两个动作处于相同的表示空间、坐标系和单位定义下。

3.5.3 成功与失败轨迹的价值

真实数据不应只记录任务最终是否成功，还应保留执行过程中的观测、动作和状态。

成功轨迹可以提供有效行为示范；失败轨迹可以帮助定位模型在哪些状态下失效，以及问题是否来自感知、动作接口、接触或控制。失败轨迹并不意味着可以不加区分地作为正确动作监督，需要根据具体训练目标选择使用方式。

3.6 迁移方法四：分级验证

仿真策略进入真实机器人之前，需要逐步验证接口、运动和物理交互。分级验证的原则是：只有当前阶段通过，才进入风险和复杂度更高的阶段。

阶段 主要检查内容 目标
仿真回归 固定随机种子，重复执行任务 确认仿真结果稳定且可复现
接口自检 Topic、TF、单位和方向 确认通信与数据语义正确
空载低速 运动轨迹、关节限位、急停 在无负载条件下验证运动和安全机制
低能量接触 接近方向、力限制、速度限制 验证真实接触行为
完整任务 成功率和异常复盘 验证端到端任务表现

如果低能量接触阶段出现接触力超过预期等问题，应暂停测试，检查接触参数、力限制、传感器标定和控制器配置，而不是直接进入完整任务。每个阶段的速度、力和安全阈值都应依据具体机器人、末端工具和任务风险确定，不能使用未经验证的通用数值。

3.7 Locomotion 的 Sim2Real：重点跨越动力学差距

Locomotion
指机器人行走和移动，例如双足机器人行走、四足机器人奔跑或在不平整地面上保持平衡。

这类任务中，机器人与地面之间持续发生接触，整体运动高度依赖动力学和执行器响应。因此，质量、摩擦、电机特性和控制时延是重要的迁移因素。

常见训练方式包括：

  • 强化学习：通过奖励函数评价运动结果，逐步更新策略。
  • 模仿学习：利用参考动作或专家演示训练运动策略。

仿真训练可以采用奖励学习或参考动作跟踪。为提高真机适应能力，可以对质量、摩擦、电机参数和时延进行合理随机化与适配。

最终，策略需要通过真实机器人的低层控制接口执行，常见控制目标包括关节位置或关节力矩。具体采用哪种方式，取决于机器人硬件和控制系统支持的接口。

3.8 VLA / WM 的 Sim2Real：重点跨越感知、数据与接口差距

VLA（Vision-Language-Action）将视觉、语言和动作联系起来，根据环境观测和任务指令生成机器人动作。WM（World
Model）关注对环境状态及其变化规律的建模，可以用于预测或推演环境变化。

VLA / WM
的迁移不仅涉及模型本身，还涉及数据来源、动作接口和真机闭环执行。

3.8.1 预训练与数据

模型可能利用互联网图文数据学习视觉与语言知识，也可能利用仿真和真机示范学习机器人观测与动作之间的关系。

互联网图文数据能够提供广泛的视觉语义信息，但通常不能直接替代包含机器人状态和动作的任务示范数据。机器人操作策略仍需要与具体任务和动作表示相匹配的数据。

3.8.2 动作接口适配

模型输出动作与真实机器人控制接口之间需要进行明确的适配，重点包括：

适配对象 需要核对的内容
坐标系 相对位移还是绝对位姿，参考哪个坐标系
单位 角度与弧度、米与毫米等是否一致
频率 模型推理频率与底层控制频率如何匹配
夹爪语义 数值表示张开还是闭合，范围如何定义

例如，模型输出末端相对位移，而真机接口要求基座坐标系下的绝对位置，就需要在适配层完成正确转换。如果模型和真机对夹爪数值的开合方向定义相反，也应通过明确的映射规则转换。

当模型输出语义本身正确时，应优先修正接口适配，而不是为了适配某一款硬件而修改模型。

3.8.3 真机闭环执行

真机执行不应被理解为模型一次输出完整动作序列后，机器人不再观察环境地执行到底。真实环境可能在执行过程中发生变化，因此需要重新获取图像和状态，根据最新观测滚动生成后续动作。

模型可以预测一段动作，但系统可以只执行其中一部分，再重新观测并更新后续动作。执行窗口的长度需要综合考虑模型推理延迟、控制频率、任务速度和环境变化。

3.9 仿真评测结果与真机可靠性的关系

仿真 Benchmark
的成功率反映模型在特定仿真任务、数据和评价协议下的表现。它是策略能力的重要证据，但不能单独证明真实机器人系统可靠。

例如，模型在 LIBERO
中取得较高成功率，并不意味着真机上的相机外参、TCP、关节零位、接触摩擦、控制时延和动作接口已经正确。部署前仍需要进行接口自检、分级验证和小规模真机测试。

3.10 本章总结

Sim2Real
是模型、数据、几何、物理、控制和任务环境共同参与的系统工程问题。常见迁移方法各有侧重：

方法 核心思路 主要目标
标定与系统辨识 测量真实系统并更新模型参数 减小几何和动态响应差异
域随机化 在合理范围内改变仿真条件 提高策略对变化的适应能力
少量真实数据适配 利用真机轨迹更新策略 修正仿真未覆盖的差异
分级验证 逐步提高真机测试复杂度 控制部署风险并验证系统可靠性

Locomotion 的迁移重点通常落在动力学、接触和执行器响应上；VLA / WM
则需要特别关注感知数据、动作接口和闭环执行。两类任务都不能仅凭仿真成功率判断真机可靠性。

总结：从仿真建模到真实机器人执行

机器人仿真、模型描述与通信、Sim2Real
并不是彼此独立的知识点，而是机器人开发流程中的连续环节。

仿真环境提供可控的验证条件；URDF、SDF 和 ROS 2
将机器人结构、软件模块和控制接口组织起来；Sim2Real
则负责处理仿真与真实系统之间无法完全消除的差异。

从工程角度看，一套可靠的机器人系统至少需要满足以下条件：

  1. 模型正确：机器人结构、坐标系、碰撞几何和物理参数能够合理描述真实机构。
  2. 接口明确：模块之间的数据格式、单位、坐标系、时间戳和动作语义保持一致。
  3. 闭环有效：控制命令能够被执行，状态反馈能够被读取，任务过程可以持续观测。
  4. 实验可复现：任务配置、运行日志和评价指标得到保存。
  5. 真机验证充分：通过标定、参数辨识、真实数据适配和分级测试，逐步确认系统在实际环境中的表现。

仿真可以降低试错成本，但真实机器人最终仍然受到物理规律、硬件能力和现场环境的约束。工程开发的目标不是让仿真结果看起来完美，而是建立一套能够解释差异、定位问题并逐步验证真实表现的完整流程。
