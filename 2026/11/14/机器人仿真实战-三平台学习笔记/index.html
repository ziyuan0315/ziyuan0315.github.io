1. 从机器人运动学走向可执行的仿真任务

在前面的学习中，我们已经接触过坐标系（Frame）、位姿（Pose）、正运动学（Forward Kinematics，FK）、逆运动学（Inverse Kinematics，IK）和雅可比矩阵（Jacobian）。这些知识回答的是：机器人由什么结构组成、关节变化如何影响末端位姿，以及如何根据末端目标求解关节变量。

但一个能够计算 FK 和 IK 的机器人模型，还不等于一个能够执行任务的机器人系统。要让机器人在仿真中完成抓取或导航，至少还需要把模型、环境、控制输入、状态更新和结果记录组织起来。

一个最小的仿真任务闭环可以概括为：

因此，仿真环境不只是一个三维展示窗口。只有当程序能够修改控制输入、推进系统状态，并通过画面或日志观察到结果时，它才具备了用于验证机器人行为的基本条件。

本项目采用同一类任务横向比较三个平台：每个平台都包含一个 Franka Panda 抓取方块示例和一个 AGV 导航寻物示例。这样可以把平台差异落到具体接口上，而不是只比较软件名称。

2. 用统一框架理解不同仿真平台

学习一套新的机器人仿真代码时，可以先固定检查五个问题：

  1. 模型在哪里？ 机器人、物体和环境通过什么文件或对象建立？
  2. 状态在哪里？ 关节位置、速度、机器人位姿由什么对象保存？
  3. 控制入口在哪里？ 程序通过什么接口发送关节或底盘命令？
  4. 仿真如何推进？ 哪个函数让系统进入下一个时刻？
  5. 结果如何验证？ 是否有画面、状态日志、轨迹或可回放数据？

这五个问题贯穿整个项目：

平台 模型入口 状态 / 控制入口 推进入口 主要证据
Swift / Robotics Toolbox rtb.models.Panda()、Swift 几何对象 robot.q、几何对象的 T env.step(dt) headless 日志、Swift 3D、GIF / CSV
MuJoCo MjModel.from_xml_path()、MJCF MjData 中的 qpos、qvel、ctrl mujoco.mj_step() Viewer、GIF、CSV
Isaac Sim USD 资产、World、机器人类 get_joint_positions()、ArticulationAction、轮子动作 world.step() GUI、终端日志、CSV

三个平台并不是简单的“低级、中级、高级”关系。它们的抽象方式和重点不同，是否适合某个任务，需要结合任务是否依赖动力学、接触、传感器、场景规模和数据生成能力来判断。

脚本中的 move_to() 没有直接把机器人瞬间设置到目标关节角，而是按离散时间步逐渐更新关节状态：

对应的控制关系可以写为：

q˙=clip⁡(Kp(qtarget−q),−q˙max,q˙max)\dot{q}=\operatorname{clip}\left(K_p(q_{target}-q),-\dot{q}_{max},\dot{q}_{max}\right) q˙​=clip(Kp​(qtarget​−q),−q˙​max​,q˙​max​)

qk+1=qk+q˙kΔtq_{k+1}=q_k+\dot{q}_k\Delta t qk+1​=qk​+q˙​k​Δt

这里的 gain 是比例增益，np.clip() 限制每个关节的速度指令，避免一次更新过大。脚本随后调用 FK 计算末端位置，并调用 env.step(dt) 更新 Swift 场景。

需要准确理解这段代码的性质：它是一个基于关节位置误差的简化运动学控制演示。脚本直接更新 robot.q，没有建立真实电机、电流、力矩、惯性和接触动力学模型。因此，不应把它描述成真实机械臂驱动器的完整闭环仿真。

3.4 Swift AGV：A* 路径与传感器范围展示

A* 算法通过四邻域搜索生成路径，启发函数使用曼哈顿距离：

h(n)=∣xn−xg∣+∣yn−yg∣h(n)=|x_n-x_g|+|y_n-y_g| h(n)=∣xn​−xg​∣+∣yn​−yg​∣

因为每次只允许上下左右移动，且每一步代价相同，曼哈顿距离与该栅格运动规则相匹配。路径中的每个栅格节点再通过 grid_to_world() 转换为 Swift 世界坐标。

4. MuJoCo：从模型描述到物理时间推进

与 Swift 示例相比，MuJoCo 的核心变化是：机器人模型、状态、控制输入和仿真推进被明确区分。模型由 MJCF 描述，运行状态保存在 MjData 中，执行器根据控制输入和当前物理状态产生响应。

4.1 MjModel 与 MjData

Panda 示例通过 XML 加载模型：

可以先这样理解：

  • MjModel：模型结构和参数，包括刚体、关节、几何体、执行器、惯性和仿真配置；
  • MjData：某一时刻的运行状态和计算结果，包括位置、速度、控制输入、接触信息和派生量。

几个核心变量需要区分：

变量 含义 是否等于控制命令
data.qpos 广义位置，例如关节角和自由刚体位姿 否，是系统状态
data.qvel 广义速度 否，是系统状态
data.ctrl 发送给执行器的控制输入 是，执行器输入
data.xpos 刚体在世界坐标系中的位置 否，是由当前状态计算得到的派生量

不要把 qpos 和 ctrl 混为一谈。直接修改 qpos 是直接改写系统状态；修改 ctrl 则是向执行器发送目标或控制输入，后续状态是否变化以及如何变化，取决于执行器模型和物理仿真。

4.2 为什么 nq、nv 和 nu 不相等？

源码运行日志记录：

这三个量分别表示广义位置维度、广义速度维度和控制输入维度。

Panda 机械臂本体包含七个旋转关节和两个夹爪手指关节；场景中还加入了一个带 freejoint 的方块。自由关节的位置由三维平移和四元数姿态表示，需要 7 个 qpos 分量；其速度由三维线速度和三维角速度表示，需要 6 个 qvel 分量。因此，自由关节的 qpos 和 qvel 维度不同，整体上就会出现 nq=16、nv=15。

nu=8 表示模型有八个执行器控制输入。当前示例将前七个控制量用于机械臂七个关节的位置目标，最后一个控制量用于夹爪开合。两个手指关节在模型中通过耦合关系关联，因此控制输入维度不必与手指关节位置维度相同。

4.3 MJCF 模型由哪些部分组成？

mjx_single_cube.xml 通过 <include> 引入 mjx_scene.xml；场景文件继续引入 Panda 模型文件。方块通过 freejoint 获得自由运动能力，并配置了几何体、接触维度和摩擦参数。

MJCF 中常见的结构包括：

  • worldbody：世界中的刚体层级；
  • body：刚体节点；
  • joint：刚体之间的运动自由度；
  • geom：可视几何体和碰撞几何体；
  • actuator：执行器模型；
  • keyframe：预设状态或控制关键帧；
  • option：仿真步长、积分器等设置。

本项目引用的 Panda 场景设置了 timestep="0.005"，即每次仿真步推进 5 ms，对应 200 Hz 的仿真步频。

4.5 mj_forward() 与 mj_step() 的区别

这两个函数在阅读 MuJoCo 代码时非常容易混淆。

  • mj_forward(model, data)：根据当前状态重新计算运动学、碰撞、动力学等派生量，不推进仿真时间；
  • mj_step(model, data)：执行一次仿真步，计算系统动力学并推进状态和时间。

例如，程序直接修改了 data.qpos 后，如果马上读取依赖该状态的 data.xpos，而没有先执行正向计算，那么派生量可能仍对应修改前的状态。此时应调用 mj_forward()，让派生数据与当前状态重新对齐。

4.6 MuJoCo AGV：场景进入了物理引擎，但底盘仍是简化运动学模型

04_mujoco_agv_navigation.py 在运行时通过 build_xml() 生成 MJCF，并保存为 data/mujoco_agv_navigation.xml。场景中包含地面、障碍物、目标、AGV 车体和一个 Mocap 传感器范围圆盘。

这个 AGV 的关键结构是三个关节：

它们分别允许 X 平移、Y 平移和绕 Z 轴旋转。车轮在 XML 中只是几何体，并没有独立的轮子关节和轮速执行器。因此，这不是一个严格的差速 AGV 模型，而是一个具有三个独立平面自由度的教学模型。

控制循环中，程序先计算当前位置到 waypoint 的向量，再计算目标朝向：

θtarget=atan2⁡(Δy,Δx)\theta_{target}=\operatorname{atan2}(\Delta y,\Delta x) θtarget​=atan2(Δy,Δx)

角度误差经过 angle_wrap() 归一化到 [−π,π)[-\pi,\pi)[−π,π)。随后代码把目标 X、Y 和 yaw 写入 data.ctrl，但 MJCF 中三个 position actuator 的 kp 都设置为 0，因此这些 ctrl 并不会通过位置执行器产生有效驱动力。源码注释也明确说明：data.ctrl 在这里用于记录控制器目标，真正的位置更新由程序直接限幅修改 qpos 完成。

每次循环的平移增量被限制为 0.018 m，yaw 增量被限制为 0.07 rad。因为仿真步长是 0.02 s，0.018 / 0.02 = 0.9 m/s 只能理解为按位置增量折算的名义移动速率，不能当作由轮速和动力学产生的真实底盘速度。

该模型能够把地图障碍物、目标和 AGV 放进同一个 MuJoCo 场景，也能生成 GIF 与 CSV；但它没有建立差速轮运动学、轮胎接触、轮速闭环和完整的碰撞避障控制。

传感器范围由独立的 mocap body 表示，其几何体设置了 contype="0" 和 conaffinity="0"，因此它主要用于可视化，不参与正常接触碰撞。程序手动更新 mocap_pos，并使用 AGV 与目标的几何距离判定 target_found，没有真正的射线扫描或视觉感知。

另外，当前循环中的 pos 是本轮更新 qpos 之前读取的位置；目标距离和 CSV 中的 AGV 位置也基于这个读取值。因此日志更接近“本轮控制前观测”，而不是 mj_step() 后的最终状态。分析日志时必须明确数据采样时刻。

9. 从源码中总结出的工程注意事项

9.1 可视化对象不一定是物理对象

Swift 中的桌面、方块和 AGV 主要用于展示；MuJoCo 的 Mocap 传感器圆盘关闭了碰撞交互；Isaac Sim 中 VisualCuboid 用于显示目标和 waypoint，而 DynamicCuboid 用于动态物理对象。阅读代码时要分别检查渲染几何体和碰撞几何体，不能只看画面判断物理行为。

9.2 直接修改状态与发送控制命令是两回事

data.qpos 表示当前广义位置，data.ctrl 是执行器控制输入。直接写 qpos 相当于改写状态；写 ctrl 则要通过执行器和动力学模型影响状态。MuJoCo AGV 示例的 kp=0 执行器和手动 qpos 更新，正好说明了为什么不能只看到 data.ctrl 就认为机器人是由执行器驱动的。

9.3 规划路径不等于安全可执行轨迹

本项目中的 A* 主要在二维栅格上把机器人近似为一个点。真实机器人有车身尺寸、转弯半径、定位误差和制动距离。工程中通常需要对障碍物进行膨胀处理，或在配置空间 / 代价地图中考虑机器人 footprint。还需要对路径进行平滑，并检查完整轨迹上的碰撞风险。

9.4 全局规划不等于实时避障

当前 AGV 示例在开始时生成静态路径，随后跟踪 waypoint。没有传感器持续更新障碍物，也没有局部规划器和动态重规划。真实系统通常需要感知更新地图、局部避障或重新规划；遇到动态障碍物时，不能把“重新跑一次 A*”视为全部解决方案，还要考虑实时性、局部安全和恢复策略。

9.5 状态日志必须带有明确的采样时刻

控制循环通常是“读取状态 → 计算命令 → 应用命令 → 推进仿真”。如果日志在 step() 前写入，它记录的是动作执行前状态；如果希望评估动作执行结果，应在 step() 后再读取状态，或者同时保存 pre-step 和 post-step 两组数据。否则，日志与画面可能看起来有一个控制周期的偏差。

9.6 抓取成功需要独立的物理和任务指标

控制器报告任务结束，不代表物体一定被可靠抓取。更完整的抓取评测至少应检查：物体是否离开支撑面、夹爪与物体的接触是否稳定、搬运过程中是否滑落、放置后物体是否进入目标区域，以及任务是否在限定时间内完成。

9.7 仿真不等于 Sim2Real

本项目主要完成仿真平台和任务控制链的入门演示，没有连接真实机器人，也没有完成仿真策略向真实机器人迁移。真实部署还需要处理质量和惯性误差、摩擦差异、执行器延迟、传感器噪声、相机标定、坐标系对齐、安全约束和通信时延等问题。

因此，本文最后讨论的 Sim2Real 是从本项目自然延伸出的下一阶段问题，而不是这七份脚本已经实现的功能。

10. 综合练习：设计一个具备主动感知能力的 AGV 搜索任务

题目

假设 AGV 按照全局路径到达目标附近。相机检测到目标，但目标被障碍物部分遮挡，当前视觉模型的判断置信度不足。请设计一个更可靠的搜索流程，并说明全局规划、局部运动、视觉感知和数据记录分别承担什么职责。

参考答案

可以将“主动调整观察位置”和“多次视觉观测综合判断”结合起来，而不是在第一次没有检测清楚时直接判定目标不存在。

这里需要注意三个原则：

  1. 未检测到不等于不存在。 目标可能被遮挡、处于视野之外，或受到光照和成像质量影响。
  2. 移动观察本身也需要规划。 机器人不能为了获得更好视角而进入碰撞风险区域，新的观察位姿应满足底盘运动约束和安全距离要求。
  3. 多次观测需要时间和坐标对齐。 至少应记录图像时间戳、机器人位姿、相机位姿、观察角度、检测结果和置信度，才能分析不同视角的观测是否指向同一个目标。

从数据工程角度看，这个任务不应只保存最终的一张“识别成功”图片，而应保留完整交互片段：初始遮挡图像、机器人调整动作、调整后的图像、位姿和时间戳、模型输出及最终判断。这样才能复盘模型为什么第一次没有识别出来，以及主动观察是否真正提高了任务成功率。

本项目的第 02、04、06、07 号脚本只提供了简化的路径和距离判定，并未实现上述视觉模型、多视角融合或主动感知控制。该流程属于在现有教学代码基础上的工程扩展设计。

11. 总结

通过七个脚本，可以把机器人仿真的基本工作方式串成一条清晰主线：

  • Swift 让我们先看懂机器人模型、末端位姿、IK 和关节状态更新；
  • MuJoCo 让我们进一步区分模型、状态、控制输入和物理时间推进；
  • Isaac Sim 展示了 USD 场景、机器人资产、任务控制器和差速轮控制接口如何组织在一个更完整的仿真系统中；
  • AGV 示例把栅格地图、A* 路径、waypoint 跟踪和目标搜索串联起来；
  • GIF、CSV 和运行日志为仿真结果提供了可回放、可检查的证据。

最重要的不是记住某个平台的 API，而是形成一套通用的源码阅读方法：模型在哪里、状态在哪里、控制入口在哪里、仿真如何推进、结果如何验证。

同时，必须始终区分教学简化与工程实现。运动学可视化不等于动力学仿真，程序绑定物体不等于真实抓取，静态 A* 路径不等于实时避障，仿真成功也不等于 Sim2Real 成功。只有明确这些边界，仿真结果才具有可信的工程解释。
